# GQ-008 — Live run UI
Status: approved for implementation
PRD link: GQ-008

Goal: a developer starts one local demo test and watches the guarded action trace and final result.
Inputs and types: URL string and optional goal string from a browser form; same JSON contract to `POST /api/runs`.
Outputs and types: streamed status/action events, masked browser observation images, and one terminal report with screenshot evidence or no-finding/inconclusive state.
Preconditions: one configured local demo origin; mock model mode clearly disclosed until live Meta verification.
Invariants / security: validate URL before launching Chromium; at most one run at a time; ten actions and sixty seconds including replay; server-only browser/model access; no credentials/client secrets; all browser resources close at terminal state.
Happy-path example: testing `/register` with a registration goal streams fill/click actions and a replay-confirmed seeded failure.
Failure-path example: external URL gets HTTP 400 without browser launch; unsupported goal or failed browser action is inconclusive with attempted-action trace; `/health` returns no finding.
Acceptance criteria (Given/When/Then): Given a local URL, when Start is selected, then status and action log update before the terminal report, including initial navigation and replay actions. Given a verified failure, then show expected/actual, screenshot, evidence, replay steps and repro test. Given no finding, then show no bug claim. Given external URL, then reject before launch.
Given a page observation, when the run is active, then its masked browser image arrives in the event stream before the terminal report and the UI offers an enlarged view. A verified result marks the observed failure heading on the actual screenshot when its location is available; unavailable locations are left unmarked, never guessed. The preview is read-only and cannot bypass the guarded executor.
Given the run workspace on desktop, then the header identifies GhostQA without a header mode pill badge, UI icons render via `@hugeicons/react` and `@hugeicons/core-free-icons`, typography uses `Poppins`, the theme uses a grainy matte dark surface with no gradient background and soft rounded border-radius edges (>= 12px on panels and controls), the sidebar presents the current stage and progress, and the content area gives the form and trace readable space. On a narrow viewport, the progress strip remains visible and the page has no horizontal overflow. Layout changes do not alter run requests or evidence semantics.
Unit test names: `tests/route.test.ts` verifies request boundary rejection and no-launch behavior.
Integration/E2E test names: seeded registration, healthy flow, and rejected URL tests after all implementation is complete.

Out of scope: accounts, stored runs, arbitrary sites, deployment, multi-run analytics.
Suggestion cards show a reason, a current masked image when the selector matches a visible element, and a labeled concept-only after preview for visual suggestions. Code suggestions show example before and suggested after text; no source edits or verified post-fix screenshot are implied.
When functional test mode is selected, the form displays quick-select chips for common functional test goals (e.g., primary navigation & links, form validation & submission, primary CTA flow, keyboard & focus navigation, console & network health) that populate the goal input on click, and `NoFindingState` displays the run's actual reason and deterministic DOM-backed fallback suggestions whenever model suggestions are empty.
While a run is active (`running === true`), a full-screen live evaluation theater overlay (`aria-label="Live evaluation preview"`) renders the real-time masked page screenshot with an animated browser chrome, scanning beam, stage progress pills, live action trace feed, and dynamic narrative text derived from the latest action and status (`describeLiveEvaluation`) explaining where on the page GhostQA is acting and what it is evaluating. The stream uses no-transform / unbuffered headers, paces stage transitions so each stage (`Validating URL` → `Observing` → `Reasoning` → `Executing` → `Evaluating` → `Replaying` → `Report`) is visibly painted before advancing, and updates the stage checklist inside the full-screen theater in real time.
The page uses a single sticky top `.app-header`, a collapsible sticky `.sidebar` with primary view navigation (`Overview` / `Workspace`), stage & action meters, and interactive stage descriptions, and opens `.main-content` with a landing view (`aria-label="GhostQA overview"`) that hides the test workspace until `Go to test workspace` (or `Workspace` in the sidebar) is clicked. Decorative eyebrows, overlines, kickers, and redundant status/hero pill badges (`.eyebrow`, `.tagline-kicker`, `.demo-state-pill`, `.demo-web-pill`, `.demo-badge-alert`, `.workspace-limit`, `.finding-badge`) are omitted across the UI. The landing view presents an interactive Problem & Solution switcher (`aria-label="Problem and solution tagline"`) with two selectable story controls (`Watch what users hit` and `See how GhostQA verifies it`) that retain the bold problem and solution statements (`AI-generated websites are everywhere — but are you sure yours actually works?` and `GhostQA runs guarded Chromium checks and rendered-design audits to deliver replay-verified evidence, not guesswork.`) and synchronize directly with the animated web browser demo (`aria-label="Animated design and workflow verification demo"`, `data-mode="problem" | "solution"`), including interactive step scrubbing, simulated network failure vs. verified replay evidence (`data-testid="demo-evidence"`), and an autonomous cursor (`data-testid="demo-agent-cursor"`) navigating the miniature website (`demo-web-navbar`, `demo-web-hero`, `demo-web-cards`) in an infinite loop without horizontal overflow on mobile.
Open questions: none for the seeded local demo; live Meta remains blocked.
